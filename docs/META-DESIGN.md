# Meta design / 설계 판단 기록 (2026-10-31)

## Goal, boundaries
- Goal: on-demand Windows triage in local PowerShell, evidence-first and human-supervised.
- Out of scope: real-time antivirus, automatic arbitrary 'repair', driver installation, telemetry, machine learning root-cause certainty.
- No persistence, scheduled tasks, registry changes, service modification, network upload, or unconsented remediation.
- Optional Defender scan has **native Defender protection-side effects** (including quarantine); must be explicitly selected.

## System interfaces and trust boundaries
1. **Collection** (`WinTriage.ps1`): Windows OS/process/CIM/event/Defender APIs are fallible; failure of one collector should warn, not erase independent evidence. Native tool execution only with explicit user flags.
2. **Classification** (`src/WinTriage.Core.psm1`): pure functions classify *event metadata*, never infer confirmed root cause or run commands. Input contains untrusted event messages.
3. **Presentation** (`SUMMARY.md`, JSON/CSV): explain evidence quality, reporting window and per-log cap. Raw event messages may include private data and must not be uploaded automatically.
4. **Distribution** (`Publish-GitHub.ps1`): explicit opt-in, owner auth, private-by-default; no GitHub token in project files.

## Decision register / 메타설계
| Problem | Decision | Tradeoff |
| --- | --- | --- |
| A single broken system interface stops all work | Isolate system snapshot and optional collectors behind warnings; preserve partial report | Partial data must never be labeled 'healthy' |
| Process PID reuse or permission-denied process start time | Exclude uncertain instance identities from growth calculations | Some system processes intentionally omitted |
| Huge Windows event logs | Capture bounded recent errors/warnings and a separate set of Defender detection IDs irrespective of Level; deduplicate by Log+RecordId | Older events and high-volume bursts may still be missed |
| Hardware errors vs software errors | Heuristic categories with cautious language and sample counts | No automatic diagnosis or replacements |
| Malware vs treatment | Explicit optional native scanner only; no removal/quarantine by our code | Defender itself may quarantine according to policy |
| Repair | Guidance and official verify-only commands first; no automatic repair | Less 'one-click' convenience, higher operational safety |
| Compatibility | Windows PowerShell 5.1 baseline; PowerShell 7 CI additional | Cannot fully simulate Windows collectors on Linux |

## Acceptance gates
- All `.ps1` and `.psm1` pass PowerShell parser (Windows CI).
- Pure classifiers pass deterministic examples and edge cases (PID reuse, unknown identities, 1116/1118, SCM 7031, WHEA).
- Windows runner: read-only `Quick`, `Events` and `Monitor` create valid manifest/SUMMARY without an exception under normal CI conditions. Defender/ClamAV scanning not invoked in CI.
- No mutations unless a user selects Defender scan. No system repairs in this milestone.
- Results and warnings are retained when individual collectors fail.

## Known gaps
- A real Windows workstation test (including elevated/non-elevated PowerShell 5.1/7 and diverse hardware) remains required.
- ClamAV was not executed with a real signature database in this environment.
- Disk SMART interrogation and auto-remediation are intentionally not implemented.


## ADR-004 (2026-10-31): explicit allowlisted privacy export

**Problem:** Regex-based redaction of arbitrary event/antivirus messages is prone to omission. Public issues may accidentally expose host names, local paths, credentials, IPs and device IDs.

**Decision:** Keep original reports local. Add a separate, user-invoked `Export-WtShareSummary.ps1` with a *pure* transformation module. The module reconstructs an intentionally narrow schema from bounded enums and counts, never copying unknown strings or identifiers. Output uses create-new semantics and there is no network operation.

**Trade-off:** Some diagnostic context is lost; a public summary cannot replace a full local investigation. Group counts themselves can disclose symptoms; explicit review remains necessary.

**Validation:** Synthetic canary fixture tests run on PowerShell 5.1 and PowerShell 7. Unsupported categories and unexpected integrity states cannot flow into the output as arbitrary text. This isolates a first pure module boundary for issue #4; OS collectors remain in WinTriage.ps1 for later staged refactoring.


## ADR-005 (2026-10-31): process and OS collector seam

**Context:** Process and system metadata collection were embedded in the entrypoint and wrote to script-level warning objects, preventing reproducible Windows access-denied scenarios in tests.

**Decision:** Move `Get-WtProcesses` and `Get-WtSystemSnapshot` into `src/WinTriage.ProcessCollector.psm1`. Inject optional read-only scriptblock providers and a sample clock for tests, but use the same native Get-Process / Get-CimInstance calls in production. Make warnings and per-PID deduplication explicit inputs. Preserve the fields and public CLI schema; leave report serialization and separate event/security/storage collectors unchanged.

**Failure policy:** A process provider error yields zero samples and a warning; an individual malformed or protected process is skipped without discarding independent rows. OS and ComputerSystem CIM failures are independently recoverable; unknown values remain null or `unknown` rather than implying health. Never guess process identity when start time is missing. No synthetic fixtures are taken from real user machines.

**Validation gate:** Mocked process/CIM failure-injection tests plus existing PowerShell 5.1/7 smoke/privacy/integration checks must pass before merge. Next PR isolates event-log and storage collectors with analogous warning and cap semantics.


## ADR-006 (2026-10-31): event collection sampling boundaries

**Problem:** Defender information-level detection events are retrieved separately from errors/warnings. Previously both queries each used `MaxEventsPerLog`, so a Defender log could return twice the advertised per-log cap. Also, failed event-log access was coupled to the entrypoint's implicit warnings state, preventing deterministic testing.

**Decision:** Move the event collector to `src/WinTriage.EventCollector.psm1` with an injectable read-only event provider, explicit `Warnings` sink, fixed lookback and max caps. Each query may fetch up to the cap, but overlapping records are deduplicated by (log, RecordId), sorted newest-first, then bounded to a TOTAL per-log cap. Record sample metadata (observed distinct records, retained count, query failures, malformed record count, whether a query reached its limit, whether the combined cap truncated rows). Preserve `events.json`, `event-summary.json`, event field names and passive mode. Add an optional `EventSampling` manifest field; this is sampled data, never a full event count.

**Failure policy:** Empty logs are ordinary; access errors keep other logs' evidence and mark the affected log incomplete. Malformed event rows are skipped and counted; single malformed records do not discard independent records. Defender detection event IDs 1116/1117/1118/1119 are searched even if their level is informational. If query size equals the cap, mark sampling incomplete/possibly truncated without claiming the actual total count.

**Limitations:** A finite query cap may omit relevant older events. The newest retained events are chosen across query results; category coverage is not guaranteed. Do not interpret an empty sampled query or an inaccessible log as evidence of health.

**Validation:** Synthetic events test overlapping Defender record IDs, total per-log cap, lost permissions, zero matching records, malformed records, and chronological order. Run on Windows PowerShell 5.1 and PowerShell 7, followed by existing passive integration tests.

## ADR-007 (2026-10-31): hardware collector failure isolation

**Problem:** CIM disk enumeration, PhysicalDisk, per-device reliability counters, PnP and MemoryDiagnostics were coupled in the entrypoint to script-scoped warnings, preventing deterministic validation on hardware-independent CI.

**Decision:** Move `Get-WtHardware` into `src/WinTriage.HardwareCollector.psm1`, use injected read-only providers for each source and a caller-supplied warning sink. Keep `hardware.json` keys, original disk/counter fields, evidence categories and public flags unchanged. A counter failure on a single physical disk becomes a per-device `CounterError` plus a warning, without dropping other physical disks. Use the pure `Get-WtStorageAssessment` classifier; missing information remains `inconclusive` and NEVER a healthy verdict.

**Boundaries:** No physical disk identity matching to CIM records, no SMART-healthy assertion from incomplete counters, no repair/registry/driver/scan operations. MemoryDiagnostics is limited to 10 recent provider events (30 days); no matching events is not a diagnostic success. PnP failures do not discard disk readings. Original raw identifiers may appear in local `hardware.json`; explicit minimal sharing continues to aggregate categories only.

**Validation:** Synthetic fixtures test one disk's counter access denied amid other disks, CIM vs physical provider failure isolation, PnP failure, empty MemoryDiagnostics and unavailable commands, plus existing Windows 5.1/7 smoke/privacy/events/integration tests.

## ADR-008: raw report schema v1 (2026-10-31)

Add additive integer ReportSchemaVersion=1 to raw manifest.json, independently of the privacy-minimized export SchemaVersion. Test-only ReportContract.psm1 validates mode-specific files, mandatory JSON fields/arrays, conservative storage states, event sampling caps, integrity state vocabulary, and Monitor CSV headers. It accepts null/missing evidence VALUES, but never missing required FIELDS or false-healthy states. Breaking changes require a new raw schema major version. Synthetic fixture tests and CI-generated read-only reports both use the same checks; no native scanners are launched.

## ADR-009: passive Defender evidence boundary (2026-10-31)

Extract read-only Defender status and capped threat history into injected WinTriage.SecurityCollector.psm1. The main CLI retains explicit opt-in native scan invocation. State and history failures are isolated, recorded as warnings, and never interpreted as no threats. Preserve security.json keys and the local report boundary. Phase 2 of #10 will extract optional native scan execution behind a dedicated explicit runner after separate review.

## ADR-010 (2026-10-31): isolated opt-in integrity execution

The CLI delegates passive status and explicit SFC/DISM verification to `WinTriage.IntegrityCollector.psm1`; only the CLI owns user-facing flags and mode validation. The module uses injected privilege, command resolver and native-runner providers. No resolver or runner is called unless a flag is true and admin privileges are confirmed. The allowed arguments are fixed: SFC `/verifyonly` and DISM `/Online /Cleanup-Image /ScanHealth`. Missing privilege/provider/executable remains skipped or unavailable; unknown exit code or missing output is indeterminate, not healthy. Each tool's failure is isolated; produced local output files are explicitly registered with the manifest. This is diagnostic-only, not remediation. Native tools can take significant time; there is no unsafe implicit process termination/timeout in this stage. Only fake runners are exercised in CI.

## ADR-011 (2026-10-31): explicit native security scan boundary

The passive Defender collector remains read-only. Native Defender `Start-MpScan -ScanType QuickScan` and ClamAV `--recursive=yes --infected` run only through a separate `WinTriage.ScanExecutor.psm1` module with explicit opt-in CLI flags. Validate both requested scan inputs before launching either scanner; no scan command is resolved or invoked in passive mode. Keep existing `security.json` outcomes, including Defender's own quarantine policy caveat. An absent ClamAV log or unknown native exit is an error/unknown result rather than 'no-detection'. Failure to run either scanner does not suppress results of the other. Injection tests invoke only fictional executors, never native scanners or real malware. No automatic deletion, quarantine command, upload or system repair is introduced.

## ADR-012 (2026-10-31): protect raw report folder before collection

**Problem:** Full local reports include potentially private events, scan output, paths and account/process details. A user-supplied broad-ACL output directory could expose reports to unintended local accounts. Previous code simply inherited permissions, and Windows CI did not verify ACLs.

**Decision:** Every invocation creates a fresh per-run folder and applies a protected DACL to it before any OS data is collected. Explicit access is restricted to the current Windows user SID, LOCAL SYSTEM and BUILTIN Administrators, with inheritable child entries; independent verification fails closed if permissions cannot be applied or unexpected access principals remain. Existing older report folders are **never** modified or removed. Reject UNC/network paths and reuse/collisions. Incompatible filesystems that cannot enforce Windows ACLs cause an error rather than silently writing sensitive reports.

**Limitations:** This is not encryption or a defense from the account owner, local administrators, backup privileges or malware already running under that account. Files synced by OneDrive, third-party clients or corporate backup software may leave the PC even if stored on a local drive; users must choose a non-synchronized local output path. There is a short empty-directory creation-to-ACL window; no sensitive evidence is written in that window. Future hardening may use atomic creation ACLs where supported. Never delete old reports automatically.

**Validation:** Synthetic temporary-folder ACL tests plus Windows PS 5.1/7 passive integration must inspect the DACL before reading a report, not assume success from the exit code alone. Real workstation and managed endpoint ACL policy testing remains manual (#2, #3).

## ADR-013 (2026-10-31): privacy-minimized physical Windows field validation

Hosted GitHub Windows runners validate PS 5.1/7 and synthetic failure fixtures, but cannot certify actual Windows 10/11 hardware, endpoint policy, ACL inheritance or non-admin/elevated behavior. A separately invoked `Invoke-WtFieldValidation.ps1` runs the five existing passive diagnostics with low bounded sampling into local private folders. Every report must pass the established versioned report contract and per-run protected ACL. A pure `WinTriage.FieldValidation.psm1` reduces evidence to fixed `pass/review/fail`, scan-request, ACL and warning-presence labels; full raw warnings, host/user/device names, log contents and paths never enter the status output. Reports are retained locally, not deleted or uploaded; callers choose when to inspect and dispose them. No native scans, remediations or backups are run. Windows build/PowerShell/privilege metadata are bounded but may still reveal environment details; review status text before public sharing. Test with invented canaries only. IMPORTANT: a structural `pass` is never a conclusion of system health.

## ADR-014 (2026-10-31): enforce field-runner integration and reject report path indirection

**Gap:** The manual field-validation entrypoint was only syntax-checked in Windows CI. Its synthetic assessment module and the main read-only integration passed separately; no hosted test exercised the *composed* command, stdout privacy boundary and private report output together. Additionally, lexical `GetFullPath` and DriveType checks alone do not protect against NTFS reparse-point ancestors that resolve an output path through a junction or symbolic link.

**Decision:** Each Windows CI job now executes the full manually callable field runner in a freshly owned temporary test location and verifies exactly five passive reports, v1 schema, per-run ACL, no SFC/DISM/ClamAV output, and strictly allowlisted stdout. This is hosted-runner coverage only, not Windows 10/11 physical hardware certification. Report creation rejects existing reparse points in the output path ancestry, rechecking after parent creation and immediately after per-run creation, before setting ACLs or collecting evidence. This restriction intentionally rejects some symlinked/redirected profile configurations rather than accidentally writing sensitive reports to a different destination. Reports and their ancestors are never removed or rewritten by the field runner. The test harness cleans only its own explicitly created temporary reports.

**Residual limitations:** A malicious concurrent process with directory write access can race filesystem changes; this is not a fully atomic Windows handle-based creation/protection design. Administrators, user-owned sync services and backups remain outside the local ACL guarantee. Real managed Windows 10/11 PCs require manual testing.

## ADR-015 (2026-10-31): bounded report retention metadata review, never automated deletion

**Need:** Raw local diagnostic reports may accumulate and can contain sensitive event messages, account paths, process details and detection histories. Neither the CLI nor an automated cleanup process should assume it is safe to delete evidence. Users need a minimal, explicit view of age and disk impact.

**Decision:** New separately invoked `Get-WtReportRetention.ps1` audits a chosen, already existing local report root. It lists only immediate child directories matching the CLI run-id format; the pure-metadata module never opens raw reports, reads JSON, recurses into nested paths, follows reparse points, or echoes names/paths. Only folders with verified restricted ACLs contribute to file-count and size estimates. Other folders count toward `PermissionReview` without opening their contents. Enumeration is bounded per root and per run; any truncation, ambiguous age or access problem produces `Incomplete=True` and `Status=review`. The 'older than N days' tally uses directory creation-time metadata, which is not the same as confirmed original collection date. Review is not a deletion suggestion.

**Safety:** No delete, move, overwrite, ACL mutation, network upload, scheduled job, retention timer or automatic cleanup. Full reports remain unchanged. Metadata aggregates (counts, sizes and age) still reveal some system usage; inspect before sharing. CI uses synthetic test-owned temporary folders; only tests clean their own fixtures.

**Gate:** Both Windows PS 5.1/7 synthetic ACL and retention checks, privacy no-canary assertions, static read-only guard, schema and field-runner integration green. Real Windows 10/11 managed/redirected/synced folders remain unverified.

## ADR-016 (2026-10-31): apply report ACL at directory creation, across two PowerShell runtimes

**Former threat:** PR #17 used an ordinary inherited-ACL directory creation followed by `Set-Acl`; although it wrote no sensitive evidence until after ACL verification, there was a short **empty-folder** interval with inherited permissions. CI tests also confirmed the final ACL, but not creation-time protection.

**Change:** Construct a protected `DirectorySecurity` **before** creating the run folder, with inheritable FullControl for the current Windows user SID, LOCAL SYSTEM and BUILTIN Administrators. Windows PowerShell 5.1 uses .NET Framework `Directory.CreateDirectory(path, security)`; PowerShell 7 uses the .NET Windows ACL extension `FileSystemAclExtensions.CreateDirectory(security, path)`. No insecure two-stage fallback is permitted if either runtime lacks the method or filesystem refuses the descriptor. Recheck both reparse-point ancestry and the *actual* resulting ACL before collecting any evidence. Strengthen verification to require appropriate inheritable full-control rules, not merely allowlisted principals. The security descriptor is applied during directory creation, rather than after the new folder becomes visible.

**Compatibility and limits:** These APIs may return an already existing folder without applying the supplied descriptor. Reject preexisting names, verify actual ACL and refuse collection if any mismatch; this is **not** an atomic create-new collision guarantee against a malicious concurrent local writer. A malicious process with rights to writable ancestors can still race junction or path swaps between checks. Strict company GPO/ACL policies, redirected profiles and non-NTFS storage may legitimately fail closed. This is *not encryption*, and SYSTEM, administrators, backup agents and cloud sync can still access the report. No existing reports are changed or removed.

**References:** [Microsoft Directory.CreateDirectory security overload](https://learn.microsoft.com/en-us/dotnet/api/system.io.directory.createdirectory) and [.NET FileSystemAclExtensions.CreateDirectory](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemaclextensions.createdirectory).

## ADR-017 (2026-10-31): report owner is part of the private-data trust boundary

**Issue:** Restricting a directory's discretionary access-control list (DACL) does not fully restrict its owner. On Windows, an owner may generally be able to alter a DACL even when the owner is not explicitly listed with FullControl. ADR-016 ensured that the *creation-time* DACL has three allowed SID principals, but verification did not check the resulting descriptor's owner. A managed endpoint, external policy or unexpected filesystem state could produce an unexpected owner with authority to change ACLs.

**Decision:** Extract a purely descriptive `Assert-WtPrivateSecurityDescriptor` validator from the live `Assert-WtPrivateDirectoryAcl` wrapper. Verify the owner as a SID and reject any owner other than the current Windows account, LOCAL SYSTEM (`S-1-5-18`) or BUILTIN Administrators (`S-1-5-32-544`). Continue to reject inherited DACLs, unexpected ACE principals and deny ACEs, and require inheritable FullControl for the intended SIDs. Any mismatch stops collection *before evidence is written* and leaves existing folders untouched. The same validator is used by the metadata-only retention auditor to skip untrusted reports.

**Tests:** Synthetic `DirectorySecurity` descriptors exercise ordinary user ownership, administrator group ownership, unapproved owner, missing SYSTEM ACE, unexpected extra principal, explicit deny, and unprotected DACL, with no Windows account changes. The usual live Windows PS 5.1/7 reporter ACL and passive five-mode integrations remain the merge gates.

**Limits:** This guard is not a proof of effective access, privilege policy, directory parent integrity or race freedom. Administrators and processes holding applicable Windows privileges can bypass some DACL restrictions. Some managed machines may assign a legitimate but different owner; stop and review policy instead of weakening the allowlist automatically. No encryption, automatic repair, backup, deletion or upload is added.

## ADR-018 (2026-10-31): exclusive report-run creation without directory reuse

**Problem:** Creation-time .NET APIs from ADR-016 (`Directory.CreateDirectory` and `FileSystemAclExtensions.CreateDirectory`) return an existing directory without replacing its security descriptor. A competing local process could create the *same* run path between the preflight `Test-Path` and the .NET create operation. A protected DACL on the preexisting folder was not sufficient evidence that this invocation exclusively created it; the writer must never append to a different process's report.

**Decision:** A small project-owned C# Win32 interop wrapper (`src/WinTriage.NativeReportDirectory.cs`, compiled locally through PowerShell `Add-Type`) calls Windows `CreateDirectoryW` with the protected `DirectorySecurity` binary descriptor supplied through `SECURITY_ATTRIBUTES`. Windows reports `ERROR_ALREADY_EXISTS` (183) if creation loses a concurrent collision, even if the existing folder has an identical protected ACL. The code fails immediately, never treats an existing folder as its own, and never uses a fall-back create-or-open or separate `Set-Acl`. The security descriptor is supplied *with* creation, not attached afterwards. Unmanaged descriptor memory is released in a `finally` block. Error messages are fixed or numeric only; no raw host, user, log, path or ACL data.

**Tests:** Private matching-ACL collision is rejected directly at the native boundary. Two concurrently started test-only PowerShell processes race to create the same synthetic run: exactly one must succeed, the other must fail, and the final folder must pass ACL/owner verification. Existing report contents and permissions stay unchanged. CI runs on both Windows PowerShell 5.1 and PowerShell 7.

**Residual:** This resolves **same-name create-or-open collision**, not all parent-directory races. A concurrently replaced/mutated ancestor path can still defeat path-based pre/post checks; a future handle-relative implementation would be needed for a stronger attacker model. New report files are still created by path after validation. This is not an atomic transaction, encryption, or proof against an administrator. Managed endpoint compatibility still requires physical Windows 10/11 testing.

**Reference:** [Microsoft Win32 CreateDirectory and ERROR_ALREADY_EXISTS](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createdirectory) and [SECURITY_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/wtypesbase/ns-wtypesbase-security_attributes).

## ADR-019 (2026-10-31): keep ancestor directory handles alive while writing reports

**Threat:** ADR-018 prevents a concurrent *same-name run* folder from being silently reused, but the caller still constructs file paths and writes files after directory creation. If another process can rename an ancestor or replace it with a junction between checks, path-based writes could be redirected.

**Decision:** Following exclusive private folder creation and ACL/owner verification, acquire a disposable `ReportPathLease` covering each existing directory from the local drive root down to the new run folder. The project-owned Windows-only C# helper calls `CreateFileW` on each component using `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT`, requests only metadata access, *shares read/write but not delete*, and rejects any non-directory or reparse-point handle. It compares volume serial and file ID from `GetFileInformationByHandle` against newly opened paths, and keeps those handles until the collector ends (including error paths with `finally`). The main CLI validates the lease before each JSON/CSV/summary/manifest write and before invoking optional external scan output writers. It fails closed if handles or identities cannot be verified; no evidence is collected before acquiring the lease.

**Observed Windows runner limitation:** Even with `FILE_READ_ATTRIBUTES` and no `FILE_SHARE_DELETE`, the Windows CI runner permitted a rename of the open run directory. The original design assertion that an open directory handle blocks all such renames was **falsified by CI and withdrawn**. A parent directory's `DELETE_CHILD` rights or Windows rename semantics can permit movement despite a handle's sharing flags. The supported invariant is now **identity-change detection at a checkpoint** using volume serial/file ID and rejection of a changed or vanished path, not prevention of all renames. The test fixture attempts renaming the synthetic run and ancestor, and if the operating system permits either operation, asserts that `AssertStable` fails before restoring the original path. It also checks that handles are disposed and that a later rename works.

**Residual:** It is **not** a formal handle-relative write API: collectors still write via absolute paths, and even ordinary directory renames may remain possible while handles are held. An attacker may swap a path immediately **after a checkpoint and before a file open**; data could be redirected before the next checkpoint detects the change. Do not treat this as a complete security fix. On systems with unusual filesystem semantics or high-strength attackers, share-mode enforcement may not suffice. Obtaining each handle is not one atomic transaction; the implementation rejects reparse points and checks identities but cannot close all hostile races during acquisition. It does not protect against modification of file content by the authorized user/administrator, tampering with individual output file names, backup/sync capture or malware running in the same user context. File IDs vary by filesystem. Managed/non-NTFS compatibility and physical Windows 10/11 tests remain required. No existing report is changed or deleted.

**Microsoft references:** [CreateFile sharing and directory flags](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [GetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle).

## ADR-020 (2026-10-31): core file creation relative to the held run-directory handle

**Prior issue:** ADR-019 file-ID checkpoints catch some path changes but did not bind `Out-File` or `Export-Csv` to the already verified run directory. A local adversary who swapped the path *after* a checkpoint and *before* the next file open could redirect sensitive evidence. The path lease also did not prevent all renames in hosted Windows tests.

**Decision:** Keep the protected, verified run-directory handle from ADR-019 and create **core diagnostic files** relative to that already-open Windows directory with the user-mode Windows `NtCreateFile` API and `OBJECT_ATTRIBUTES.RootDirectory`. The object name is a single allowlisted report filename only, `FILE_CREATE` fails if an entry already exists, and `FILE_NON_DIRECTORY_FILE | FILE_SYNCHRONOUS_IO_NONALERT | FILE_OPEN_REPARSE_POINT` requests a new normal file with no symlink-following fallback. The returned file handle is transferred to a `.NET FileStream/StreamWriter`, which writes the provided UTF-8 content (PowerShell 5.1 BOM vs PowerShell 7 no BOM) without reopening it by path. The protected parent ACL remains inherited, verified by the Windows synthetic tests. `AssertStable` remains useful as a preliminary detection checkpoint, but the relative creation binds a new core file to the held directory even when its original path is later renamed.

**Scope:** `WinTriage.ps1` now creates `system.json`, `processes.json`, events/summary/security/hardware/integrity JSON, two memory CSVs, `SUMMARY.md`, and `manifest.json` this way. It does not overwrite an existing report filename, allow a traversal or alternate stream name, upload data, delete prior reports or change native scan intent. Legacy report serialization and schema-v1 validation remain gated by both PowerShell editions' CI.

**Explicit residual and compatibility:** This is an incremental mitigation, **not** a complete security boundary for every output. Optional `RunClamAV` or `RunSfcVerifyOnly`/`RunDismScanHealth` still use independently injected native-tool runners that write `*.txt` via filesystem paths; do not describe them as handle-bound. The initial directory handle may be obtained after an adversary changed its ancestor, and admin/same-user modification, backup/sync, antivirus interaction and managed/non-NTFS compatibility remain outside the guarantee. `NtCreateFile` is documented as a user-mode native Windows API using a filesystem directory `RootDirectory`, but its precise flag/parent-access edge cases need Windows version and enterprise policy validation. **Fail closed if the native API refuses creation; never fall back to path-based writing.**

**Microsoft sources:** [NtCreateFile user-mode documented interface](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile), [OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes).


## ADR-021 (2026-10-31): stream opted-in native tool output into pinned report files

**Threat:** ADR-020 secured core JSON/CSV/Markdown/manifest creation but did not bind the three optional text logs (`clamav-output.txt`, `sfc-verifyonly.txt`, `dism-scanhealth.txt`). Their previous `Out-File -LiteralPath` ran in the native executor after a path checkpoint, reopening the mutable absolute run directory.

**Decision:** Extend the existing allowlisted `NtCreateFile` + `OBJECT_ATTRIBUTES.RootDirectory` helper to return a disposable, exclusive new-file `.NET StreamWriter`. The main CLI passes a closure bound to its pinned run-directory lease into the opt-in scan and integrity executor. Before any executable is launched, the executor asks for this writer. Native stdout/stderr is piped line by line into the writer, not into a filename; it is flushed and disposed even on failure. If writer creation fails, the scan is not started (fail closed). The factory defaults to a throw for standalone executor calls; there is **no path fallback**. No implicit scan or repair is added. No log cleanup, overwrite, automatic upload or report deletion is added. Partial diagnostic output may remain after a tool failure and must not be interpreted as a clean result.

**Trade-offs:** Output is converted to strings line by line by PowerShell, not retained as raw native byte-for-byte output; source stderr/exit semantics require field review. Windows PowerShell 5.1 UTF-8 BOM and PowerShell 7 no-BOM are retained. Secure file creation is tied to an already-open directory, but earlier lease acquisition, same-user/admin modification, native tools' *own* operating-system logs, enterprise policy, and physical Windows 10/11 compatibility are outside the guarantee. The `OutputDirectory` argument remains for compatibility/validation but is **not used to open native tool logs**. A malicious local user with sufficient privileges can still modify the newly created files after opening. This is a mitigation, not an atomic security sandbox.


## ADR-022 (2026-10-31): fail early on sustained ancestor swaps during path-lease acquisition

**Threat and observation:** ADR-019 acquired root-to-run directory handles sequentially but rechecked the entire chain **only after** the last handle had opened. A concurrent process could rename or replace an ancestor during acquisition and cause subsequent descendants to be opened through a different path before the first identity check. The already handle-bound output writers from ADR-020/021 prevent reopening an ordinary file path later, but cannot prove the *original* run directory was pinned.

**Decision (incremental):** After **each** component is pinned with the existing `CreateFileW` + `FILE_FLAG_OPEN_REPARSE_POINT` metadata handle, immediately call the existing `AssertStable()` over the acquired prefix, before traversing another child. If a sustained rename/replacement has changed a pinned path, abort and dispose **all** handles. A new `AcquireForSyntheticTest(directory, afterPin)` hook is exclusively for deterministic test interleavings: after the synthetic parent is pinned but before a child is attempted, rename the test-owned parent and replace it with an empty decoy folder. If Windows permits this rename, assert failure before the test hook sees the run directory; restore the fixture and confirm the original protected ACL. If Windows denies the rename, verify normal acquisition and report the conditional skip. A separate thrown-hook fixture checks failure recovery. The production `Acquire` calls the same code with a **null** test hook; there is no new CLI flag and no new Windows native interop.

**Limits:** These additional checkpoints increase initial directory-open work (approximately quadratic with path depth) and can fail on unusually restrictive Windows policies; we do not silently fall back to path-only writes. An attacker able to change and restore a path *between* checks may still escape detection. The gap from `CreateDirectoryW` to acquiring the first report handle remains, as does non-atomic parent-to-child handle binding. The checkpoint also does **not** prove each child handle is an object-manager-relative child of the pinned parent; that would need a carefully reviewed native handle-relative traversal and creation API. A same-user/admin process can still tamper with files after creation. Do not describe this change as race-free.

**Verification:** Both Windows PowerShell 5.1 and PowerShell 7 CI run `tests/ReportPathAcquisition.Tests.ps1`, the established security fixtures, full passive five-mode integration and static safety preflight. Tests may remove **only disposable synthetic folders**. No existing report changes, native antivirus scan, SFC/DISM run, system repair or upload.


## ADR-023 (2026-10-31): test-only parent-relative directory traversal research

**Prior gap:** ADR-022 retries the identity lookup on every path prefix, but those lookups are still **absolute path names**, not open-from-pinned-parent operations. A parent can be swapped and restored between tests; no atomic parent→child provenance is established. Production modifications using undocumented native flag combinations are unacceptable without review.

**Public Windows documentation:** User-mode `NtCreateFile` explicitly accepts a `RootDirectory` handle and a relative `ObjectName`. `FILE_DIRECTORY_FILE` requests a directory. `FILE_OPEN_REPARSE_POINT` requests opening the reparse point rather than following it. However, the current published **user-mode directory-option compatibility list** does not clearly certify the exact `FILE_DIRECTORY_FILE | FILE_SYNCHRONOUS_IO_NONALERT | FILE_OPEN_REPARSE_POINT` combination. `OBJECT_ATTRIBUTES` documents `OBJ_DONT_REPARSE`, while the user-mode `NtCreateFile` page's attribute description is narrower. These documents do not establish that concurrent junction conversion, renamed ancestors or all filesystem filters are protected against redirection. A forum or hosted runner observation cannot settle the support contract.

**Decision:** Do **not** modify `src/` or the production `ReportPathLease.Acquire` flow for this unqualified API combination. The probe does not request any file create, modification or delete. Its synthetic PowerShell fixture compares the child volume/file ID before a swap, then (if Windows permits) renames **only a GUID-named test-owned pinned parent or its unpinned ancestor**, creates an empty test-owned decoy with a different ID, and observes whether the relative lookup still identifies the original child or fails. Any success opening the decoy through the held parent fails the test. If the pinned parent cannot be renamed, the fixture attempts to move a different, **unpinned test-only ancestor**. If both moves are blocked but native relative open works, it closes the ordinary handle and explicitly repins **only a synthetic test parent** with `FILE_SHARE_DELETE` enabled so a rename can be attempted deterministically. The shipping lease does not acquire this right or change its share mode. If even the test-only option cannot move, mark that swap SKIP. A known unsupported native option or blocked directory moves are recorded explicitly as SKIP, **not** proof of safety. Reject malformed leaf names in the research helper; release unmanaged memory and handles on all paths. Both PowerShell editions run it along with existing security tests. Production never imports the research C# file.

**Go/no-go before production code:** Require a documented and reviewed supported combination, a clear parent/root rights and no-reparse policy, direct handle-derived ACL/owner validation, a create-to-handle provenance plan, deterministic tests for rejection under swaps/junctions, and physical Windows 10/11 plus managed filesystem evidence. ## ADR-024 (2026-10-31): read pinned-directory owner and DACL by handle in synthetic research

**Problem:** ADR-023 showed relative directory identity stability on one hosted Windows configuration, but the production ACL check still uses `Get-Acl -LiteralPath`, a fresh *path* resolution. This cannot establish that the directory whose ACL was checked is the same object already pinned for report writing.

**Published Windows contract:** Microsoft documents `GetKernelObjectSecurity(HANDLE, OWNER_SECURITY_INFORMATION | DACL_SECURITY_INFORMATION)` as returning a self-relative security descriptor. The handle must have been **granted READ_CONTROL when opened**; reading a SACL would additionally require ACCESS_SYSTEM_SECURITY and is deliberately out of scope. `GetSecurityInfo` with `SE_FILE_OBJECT` is a second documented handle-based option, but introduces an explicit LocalFree lifetime and is not used by this initial probe. A protected DACL is represented by `SE_DACL_PROTECTED`; .NET's `DirectorySecurity.AreAccessRulesProtected` and the existing `Assert-WtPrivateSecurityDescriptor` policy can assess the retrieved owner/DACL/ACE rules after materializing its binary descriptor.

**Decision:** A **test-only** `tests/HandleSecurityProbe.cs` opens an existing synthetic, direct directory with `CreateFileW(FILE_READ_ATTRIBUTES | READ_CONTROL)`, flags `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT`, no file create, and test-only `FILE_SHARE_DELETE` to exercise rename. It validates directory/reparse attributes via `GetFileInformationByHandle`, requests a bounded two-call `GetKernelObjectSecurity` owner/DACL buffer, and decodes it with .NET `DirectorySecurity.SetSecurityDescriptorBinaryForm`. Bad handles, missing READ_CONTROL, invalid descriptors and queries fail closed. No SACL or permission mutation is performed by the native helper.

**Test matrix:** A GUID-named test-owned temp fixture creates a protected private run via the existing security constructor; compares path-based and pinned-handle owner/DACL with the existing policy; checks refusal on a handle opened without READ_CONTROL; and conditionally moves only that test run while the handle is held. If the move succeeds, create a **synthetic decoy** at the old path, give only the disposable decoy a deliberately incomplete DACL, reject that decoy with the existing ACL policy, and verify the pinned handle continues returning the original file identity, owner and DACL. If current sharing/policy blocks rename, report an explicit SKIP, not evidence of immovability. Dispose handles; cleanup touches only the GUID-owned fixture. CI logs print no account SID, ACL/SDDL, native path or personal report contents.

**Strict no-go:** Do not change `src/`, production handle desired access/share mode, or switch `Enter-WtReportPathLease` to this new method on hosted-runner evidence alone. The `CreateDirectoryW`→first handle acquisition race, initial parent/child lineage, in-call swaps, junction/reparse races, non-NTFS behavior, managed policies, Windows 10/11 device coverage, same-user/admin tampering and handle-derived security descriptor TOCTOU vs later ACL mutations remain unresolved. A future production proposal requires independently reviewed compatibility, a complete fail-closed error model, and field validation. Issues #2/#3 remain OPEN.

## ADR-025 (2026-10-31): research only — atomic return-handle directory creation relative to a pinned parent

**Threat:** ADR-024 proves a handle can retain the original owner/DACL after a synthetic path substitution. Production still has a gap between absolute-path CreateDirectoryW and a later absolute-path handle open. A valid ACL retrieved through the latter handle does not prove it is the directory just created. This is a *creation lineage* research step, not a production migration.

**Documented baseline:** Microsoft Win32 CreateDirectoryW accepts SECURITY_ATTRIBUTES but returns a BOOL, *not* a handle to the new directory. User-mode NtCreateFile documents RootDirectory-relative ObjectName, SECURITY_DESCRIPTOR applied on creation, FILE_CREATE refusing existing objects, FILE_DIRECTORY_FILE for directory objects and a resulting FileHandle. Use FILE_DIRECTORY_FILE | FILE_SYNCHRONOUS_IO_NONALERT with matching SYNCHRONIZE access, avoiding FILE_OPEN_REPARSE_POINT: the user-mode documentation does **not** list that flag as compatible with FILE_DIRECTORY_FILE. **Research-only implementation:** tests/DirectoryCreationProbe.cs opens a test-owned existing direct parent with FILE_READ_ATTRIBUTES | FILE_TRAVERSE | FILE_ADD_SUBDIRECTORY | READ_CONTROL and *test-only* FILE_SHARE_DELETE, then calls NtCreateFile with a strict single-leaf allowlist, RootDirectory = pinned parent, exclusive FILE_CREATE, an explicit protected private descriptor supplied in OBJECT_ATTRIBUTES.SecurityDescriptor and the documented synchronous directory flags. It directly returns the newly created directory's own SafeFileHandle (not a later path open). It checks file type/reparse attributes and FILE_CREATED result, disposes all unmanaged allocations and safe handles on failure, and has no path-based fallback. The caller immediately uses ADR-024's handle-based GetKernelObjectSecurity and the unchanged private owner/DACL policy. Test-only creation is restricted to a newly generated GUID temporary fixture; no real reports are accessed.

**Synthetic cases:** Validate owner/DACL on the just-created handle, compare its volume/file ID to a separate synthetic path probe, refuse name collisions and malformed names, refuse use after parent close. Then conditionally rename the *held* disposable parent, create an empty different parent at its former path and create a second child relative to the held handle. The child must be in the moved original parent, never the decoy, or the test fails. A blocked test-only rename is explicitly SKIP, not evidence that rename cannot happen. CI must pass on Windows PowerShell 5.1 and PowerShell 7 with existing synthetic, passive integration and static tests. No SIDs/SDDL or personal filesystem path contents appear in status output.

**No-go:** DO NOT transplant the probe to src/ on a green CI alone. A complete root-to-parent trusted handle chain, formal no-reparse rules (including in-call change), filesystem/policy differences, security descriptor ownership/canonicalization, same-user/admin tampering, unusual Win32/NT security descriptors, and Windows 10/11 physical/managed tests must be reviewed first. Testing the *last creation hop* is not an end-to-end race-free sandbox. No user report deletion/upload, no implicit scans or repairs. Issues #2/#3 remain OPEN.

## ADR-026 (2026-10-31): synthetic pinned-anchor multi-hop traversal and private creation

**Question:** ADR-025 demonstrated parent-handle-relative private directory creation, but the initial parent was still opened by absolute path. Can a multi-hop path below an *already trusted* anchor be traversed with returned directory handles rather than repeated absolute path opens, then used to create a private run?

**Documentation and crucial no-follow choice:** Microsoft's user-mode \`NtCreateFile\` documentation describes filesystem \`RootDirectory\`, single relative object names, \`FILE_OPEN\` and \`FILE_OPEN_REPARSE_POINT\`. The documented compatibility list for \`FILE_DIRECTORY_FILE\` does not include \`FILE_OPEN_REPARSE_POINT\`; successful ADR-023 hosted trials with that exact combination are **observations, not a support guarantee**. This research uses **type-neutral** \`FILE_OPEN | FILE_SYNCHRONOUS_IO_NONALERT | FILE_OPEN_REPARSE_POINT\` (i.e. omits \`FILE_DIRECTORY_FILE\`) and then rejects anything without directory attributes or with reparse attributes on the *returned handle*. Opened hop handles have READ_CONTROL, FILE_READ_ATTRIBUTES, FILE_TRAVERSE and FILE_ADD_SUBDIRECTORY for subsequent research creation; they also carry test-only FILE_SHARE_DELETE for renaming. Intermediate handles remain open until the last one has been acquired. No path fallback, no file create, and no write/delete operation occurs in the traversal helper.

**Scope:** Add \`tests/HandleChainProbe.cs\` and a PowerShell 5.1/7 synthetic test. Establish an anchor by a single \`CreateFileW\` open of a freshly created GUID-owned fixture, hold that handle, then traverse two named existing directory hops with \`OBJECT_ATTRIBUTES.RootDirectory\` for each hop. Compare returned final ID with an independent synthetic path identity. Reject malformed/absolute/traversal/ADS leaf names, ordinary files, closed handles and an optional synthetic junction (SKIP if junction creation is denied by environment; if created, a followed target is a test failure). If supported, move the held anchor and create a decoy tree at the former path; a fresh rooted multi-hop walk must reach the original descendant, not the decoy. Use the returned final handle with ADR-025's existing test-only exclusive relative directory creation, and ADR-024's handle-derived owner/DACL gate, verifying the new private run ends under the original chain. The fixture is the only directory tree ever removed. No actual report, scan, upload, SFC/DISM or repair. CI logs do not expose SIDs, ACL strings or personal data.

**Limits / no-go:** An absolute \`CreateFileW\` open of the *anchor* is still a trust assumption; root-to-anchor provenance and initial creation-to-anchor pinning remain unsolved. Type-neutral no-follow open plus a post-open reparse-attribute check is **not an atomic non-redirection guarantee** under in-call filesystem/filter behavior or concurrent reparse mutation. The test is a reproducible hosted-Windows experiment, not proof of Windows 10/11, non-NTFS, managed policy, anti-tamper or same-user/admin security. The exact parent handle rights, reparse contract, handle-relative disposal, file IDs and security descriptor enforcement must be independently reviewed before any production \`src/\` adoption. Issues #2/#3 stay OPEN.

## ADR-027 (2026-10-31): test-only anchor provenance and deterministic pre-open reparse substitution

**Boundary:** ADR-026 can traverse from a *previously trusted* directory handle, but it calls absolute-path `CreateFileW` to obtain that initial synthetic anchor. An attacker could replace that path **before the first pin**, leaving a valid but wrong object even if all later handle-relative opens are perfectly consistent. ACLs/owners on an object selected by a hostile path are not a proof of which object was intended.

**Decision:** This PR is research-only, with no changes to `src/`. Add `PinSyntheticAnchorExpectIdentity` to test-only `HandleChainProbe`: open the candidate once, compare its volume/file ID *on that same handle* to an **independently established** synthetic baseline, dispose/throw on mismatch. An identity string itself is not a secure source of trust; this is a conditional verification primitive only. Add `WalkWithSyntheticBeforeHop(anchor, leaves, callback)` for deterministic test interleavings. The existing no-callback `Walk` follows the same code path. The callback runs after a parent handle is validated and **before** the next single-leaf `NtCreateFile(FILE_OPEN)` call. The native type-neutral `FILE_OPEN_REPARSE_POINT` query and post-open reparse/directory checks from ADR-026 stay unchanged; no path fallback and no new operational Windows API.

**Fixtures:** Under one freshly GUID-named test-owned temporary root, save the original anchor file ID, move that anchor, and replace its former path with a fully valid but different decoy. Opening the decoy against the externally supplied original ID must fail; opening the relocated original against the same ID must succeed and yield the expected child. In a second deterministic boundary, move a test-owned intermediate folder **immediately before** relative open and substitute a junction to a second test-owned tree containing a plausible child; `Walk` must throw rather than follow the target. Report PASS on actual substitution/rejection and explicit SKIP when the runner denies the synthetic rename or junction creation. Tear down only the GUID-owned fixture, without following a junction during cleanup. No personal paths, SID, ACL, hostname or raw report data in CI output.

**Evidence vs guarantees:** Microsoft's `NtCreateFile` documentation describes `FILE_OPEN_REPARSE_POINT` and `RootDirectory` semantics, but a successful controlled pre-call swap cannot prove atomic safety against *in-call* reparse mutation, filter driver behavior, or an attacker with same-user/admin rights. `FILE_DIRECTORY_FILE | FILE_OPEN_REPARSE_POINT` remains without a clear published compatible user-mode contract; this probe deliberately keeps the **type-neutral** open from ADR-026. Most critically, production does **not** yet possess an independently authenticated baseline for the initial anchor. It is invalid to promote the test-only identity check to production without specifying how that baseline is securely obtained and protected. Physical Windows 10/11, reparse variants, policy and non-NTFS tests remain pending in issue #2; privacy/release review remains issue #3. **Do not deploy to `src/` on hosted-CI evidence.**

## ADR-028 (2026-10-31): fail-closed local drive spelling and read-only rooted chain experiment

**Threat / trust separation:** ADR-027 rejected a wrong anchor *only when an independently authenticated expected file ID exists*. No general trusted ID source was established. A drive-letter root (`C:\`) is a concrete filesystem object that can be pinned for a series of child opens, but the spelling, `DriveType.Fixed`, and NTFS format **do not authenticate the volume's identity or authorize its ancestors**. Remapping/mount points, reparse components, policy, and same-user/admin modifications remain open. Do not claim a full trusted chain.

**Documented basis:** Microsoft explains Win32 drive-relative paths (`C:foo`), UNC paths, device namespaces (`\\?\`, `\\.\`), reserved DOS device basenames and normalization rules in *Naming Files, Paths, and Namespaces*. A directory can be opened by Win32 `CreateFileW` with `FILE_FLAG_BACKUP_SEMANTICS`, and a held handle can anchor a relative single-component `NtCreateFile`. `GetDriveTypeW`/`.NET DriveInfo` describe media types but are **classification**, not a security-authentication primitive. A type-neutral `FILE_OPEN_REPARSE_POINT` then checking returned directory/non-reparse attributes is an observed fail-closed technique for static reparse points, not an atomic in-call proof.

**Experiment only:** `tests/RootPathPolicyProbe.cs` lexically rejects ambiguous/unsupported path spellings **before** any normalization or path open: UNC, Win32 device/extended namespace prefixes, drive-relative/root-relative paths, forward slashes, empty/.. components, ADS colons, Windows DOS reserved names, separators, trailing dot/space, unknown/non-ASCII syntax and overlong components. This intentionally narrow ASCII-only research grammar is **not** a universal Windows pathname validator and is never applied to production report paths. `HandleChainProbe.PinReadOnlySyntheticVolumeRoot` opens only the actual root of the test fixture's fixed NTFS volume with metadata/traverse rights, then `WalkRootReadOnly` descends existing direct directory components with minimal `FILE_READ_ATTRIBUTES | FILE_TRAVERSE | SYNCHRONIZE` (no WRITE, DELETE, FILE_ADD_SUBDIRECTORY, READ_CONTROL). It retains and closes parent handles correctly, refuses native errors, non-direct/reparse objects or disallowed leaf names, and does not fall back to reopening an absolute child. A disposable GUID fixture under the current temp folder supplies an independent expected file ID, and an optional locally-created junction in that fixture must be rejected. The test reads volume metadata but creates/removes **only its own temporary fixture**, never a real report.

**No-go:** A green hosted Windows 5.1/7 runner only shows this probe's compatibility for that filesystem/policy and point-in-time objects. Root identity may be substituted before the initial absolute open, and the test does not authenticate a root file-ID baseline; root to fixture can encounter reparse mount-points, access-denied or filesystem filters, and at-run-time mutation remains unproven. No production `src/` adoption or relaxation of existing report security. Physical Windows 10/11, enterprise-managed, non-NTFS and anchor-authentication evidence must be gathered under issue #2, and privacy review under #3. Both remain OPEN.

## ADR-029 (2026-11-01): read native 128-bit file identity and volume-GUID alias from held handles (research only)

**Why:** ADR-028 proved a rooted read-only lookup of a disposable folder on one hosted fixed-NTFS Windows runner. But drive letters, filesystem type and NTFS serial numbers are not independently authenticated trust roots; a *different object on the same volume* has the same volume serial. Confusing volume identity, alias spelling and file object identity can mask a substituted directory.

**Published contracts:** Microsoft `GetFileInformationByHandleEx(FileIdInfo)` returns `FILE_ID_INFO` with a 64-bit `VolumeSerialNumber` and `FILE_ID_128`. Use the entire tuple (8+16 bytes), with no fallback to truncated `BY_HANDLE_FILE_INFORMATION` 64-bit IDs (not necessarily unique on ReFS). Microsoft `GetFinalPathNameByHandleW(VOLUME_NAME_GUID)` may provide a GUID-based volume spelling for an already-open handle, but a GUID path may be unavailable on some filesystems or unmanaged mappings, and that name is an **observation, not an independent authenticity authority**. File IDs can be reused across object lifetimes and are not cryptographic attestations. No documented API here proves a trusted volume has not been remapped before acquisition.

**Decision:** Add `tests/VolumeIdentityProbe.cs`, never imported from production, with bounded, handle-only `GetFileInformationByHandleEx(FileIdInfo)` and optional `GetFinalPathNameByHandleW(VOLUME_NAME_GUID)`. Reject null/disposed handles, invalid expected fingerprints or a different full file ID; refuse silently degrading to 64-bit file IDs. Never log a file ID, volume serial, volume GUID or full filesystem path. This experiment is **metadata-only** and never modifies a drive letter, mount point, reparse point, root ACL, real report or filesystem settings.

**Synthetic test:** In `tests/VolumeIdentityProbe.Tests.ps1`, create a fresh GUID-owned temporary directory and one child. The current volume must be ready fixed NTFS or the *research case* is explicitly SKIP. Read two independent root handles and require full 128-bit file identity equality; compare their volume serial against child handles. If the handle-derived GUID volume alias is supported, require the root/child GUID prefix to agree; if not, explicitly SKIP just that observation. Then rename the **test-owned** pinned child and replace its old name with a new test-owned decoy on the same volume (if test-only rename is allowed). The decoy must have the same volume serial but a different full file identity, and `RequireFileIdentity` must reject the stale original identity. The held original must retain its identity. Closed handles and malformed baseline identifiers fail closed. All cleanup remains entirely within the GUID scratch fixture. PowerShell 5.1 and 7 run the test along with existing suite and passive integration.

**No-go:** The independently opened root handles and volume GUID alias can all be fooled by an attacker able to remap the root *before both opens*; even matching 128-bit object identity cannot establish a good anchor without an authenticated external expectation. This is not a proof of in-call reparse safety, stable persistent file IDs, non-NTFS/reparse/filter/enterprise compatibility, or immunity to admin/same-user tampering. **Do not promote to `src/` on CI evidence alone.** Issues #2 and #3 stay OPEN pending physical Windows 10/11 field validation and a privacy review.

## ADR-030 (2026-11-01): ephemeral caller-supplied anchor provenance contract (research only)

**Problem:** ADR-029 can compare 128-bit file IDs for held objects, but it cannot establish that the *first* object is the desired one. Windows volume GUID paths may have multiple aliases; file IDs may be reused over time. Reopening the same possibly-substituted path twice, comparing two handles acquired *after* an attack, or checking drive type/format/serial/GUID is **self-consistency**, not independent authentication. Persisting such identity claims across boot, mount reconfiguration, recreation or handle lifetimes would create false security assurance.

**Decision matrix for a possible future production design:**

| Proposed provenance input | Decision | Why |
| --- | --- | --- |
| Reopen same untrusted path, compare GUID/name/serial | **NO-GO** | Both handles can already reference the substituted object. |
| File ID cached on disk in a user-writable report or settings file | **NO-GO** | No authenticated baseline origin, edit protection or lifetime guarantee. |
| \`DRIVE_FIXED\`/NTFS/volume-GUID alias alone | **NO-GO** | Classifications and names are not an authority that selects an intended root. |
| Previously held independently trusted reference **within one session** | **Conditional research** | Held object can be compared with a separately opened candidate while the reference remains alive; the source of trust remains an external assumption. |
| Authenticated parent/root controlled by an OS trust boundary | **Investigation required** | Requires threat model, rights review, reparse/mount behavior, supported API contract, and physical Windows 10/11 validation. |

**Experiment:** Introduce **only** \`tests/SyntheticAnchorLease.cs\` as a scoped, disposable assertion wrapper around an *externally supplied, held reference handle*. It borrows the reference without closing it, reads the **full 128-bit file identity** using ADR-029 at construction, requires an explicitly provided nonempty caller session GUID, re-queries the held reference on each verification, rejects invalid, identical/reference, closed or different-file candidate handles, rejects a mismatched session GUID, and rejects further checks after explicit session disposal. The GUID is a lifecycle consistency token **not** a cryptographic credential; neither it nor an ID authenticates the original reference. This is intentionally not implemented in \`src/\` and does not open or modify any pathname.

**Synthetic cases:** A test-owned GUID temporary fixture supplies two separate handles to the same initial directory; validation succeeds before a deterministic rename of its logical alias. A newly created decoy at that old name shares the volume serial but fails full file ID verification, while the original held candidate remains bound to the moved object. Deliberately make a *new baseline from the decoy itself* as a negative control: it then successfully validates the decoy, demonstrating why self-certifying baselines do not establish provenance. A wrong session GUID, identical reference/candidate handle, revoked lease and disposed borrowed reference must all fail closed. Blocked synthetic rename is explicit SKIP, not evidence of tamper resistance. Cleanup touches only the disposable GUID fixture. Do **not** change real drive letters, mount points, volume metadata, ACLs or reports; do not log raw IDs, GUIDs or system paths.

**Gates:** Hosted Windows 5.1/7 CI verifies implementation and negative controls, not the security of a true initial anchor, not actual drive remapping, and not in-call reparse races. A held reference is not a substitute for an OS trust root if its provenance is uncertain. Future work needs a reviewed anchor source and physical Windows 10/11/enterprise filesystem checks (issue #2), plus privacy approval (issue #3), before any production migration. Both issues remain OPEN.

## ADR-031 (2026-11-01): no-go-only field evidence matrix and human release authorization

**Issue/intent:** #2 requires real Windows 10/11 field evidence, while #3 requires manual report ACL, privacy and release disclosure review. ADR-023 through ADR-030 have *hosted* Windows synthetic evidence and **no authenticated initial trusted volume/root**. A green Actions run does not establish that a physical workstation, synced profile or managed endpoint is supported. No production `src/` change or synthetic-to-production migration is authorized.

**Decision:** Add a strictly offline, standalone **metadata-only** Python stdlib checker `tools/field_evidence_gate.py`. It accepts a user-supplied local JSON file containing only a fixed set of enumerated labels, bounded to 32 KiB. It rejects unknown keys, free-text notes and duplicate matrices and never prints input values, paths, hostnames, serial numbers, raw diagnostics or data from other files. An explicitly neutral template is versioned under `docs/field-evidence-template.json`; it contains only `not_run`, `not_observed` and `unverified`.

**Gating matrix:** Exactly eight unique operating-system × PowerShell × privilege combinations: Windows 10 or 11; Windows PowerShell 5.1 or PowerShell 7; standard or authorized elevated. For each: five passive Quick/Events/Hardware/Monitor/Integrity modes, schema contract, per-run private ACL and `passive_scans=absent`. Explicitly track three *observed* exceptional provider scenarios (Defender unavailable, Event Log access denied, unsupported storage provider) without deliberately disabling security services. Separately track four manual review areas: independently trusted initial root, in-call reparse/mount races, real ACL/privacy and managed/synced storage. A failure, review or missing coverage blocks readiness. If an elevated run is prohibited by policy, record it as not_run; do not bypass corporate controls or claim green.

**Crucial limit:** Even a perfectly filled JSON **cannot prove real hardware observations or an authenticated initial root**. The checker always returns `decision=NO_GO` and its CLI **always exits with code 2**, including for synthetically complete evidence. Such evidence is labelled `MANUAL_APPROVAL_REQUIRED` only, not GO. Only a separate, authorized human security/privacy release decision, outside this checker, can review actual local findings. No input or program output is automatically uploaded.

**Regression:** Dependency-free `tests/FieldEvidenceGate.Tests.py` uses invented labels and checks missing matrix rows, unobserved provider cases, mismatched privileges, failed ACL/schema, unexpected native scan, duplicate input, free-text canary rejection, oversized/invalid JSON, and an all-pass forged manifest remaining NO_GO. Run as an *ordinary CI test* on both Windows jobs. This deliberately does not gate ordinary PR merging (NO_GO for production is the expected state), does not run any optional Windows tools, and cannot close #2/#3.

**Outstanding:** Genuine Windows 10/11 local field-validation results, review of unsupported/redirected providers, independently authoritative root provenance, enterprise profile/cloud sync, privacy disclosure UX, documented release approver and signoff. Keep #2 and #3 OPEN. This research checklist must not be treated as a signed attestation.

## ADR-032 (2026-11-01): manually transcribed, privacy-bounded field status snapshots (PR #37)

**Problem:** ADR-031's pending-only eight-cell JSON is error-prone to edit by hand. The passive field runner emits fixed mode/status labels, but also retains sensitive raw reports. A convenience tool must never ingest those reports, leak free text, infer health, or turn self-asserted values into release approval.

**Decision:** Add the *separate*, explicit Python-stdlib `tools/field_status_recorder.py`. An authorized operator reads the already existing fixed console status lines and manually enters exactly five `Mode:Validation:Contract:PrivateAcl:PassiveNativeScans:Warnings` tuples, a chosen OS/shell/privilege cell and `--observed-local-only`. The tool accepts only strict enumerations, uses the ADR-031 metadata validator, requires all eight cells in the source and refuses to rewrite a previously recorded cell. It preserves all remaining pending cells, provider-negative observations and manual security reviews. Warnings cannot become `pass`; a failed contract/ACL or unexpected passive native scan requires `fail`. The worst observed per-mode contract/ACL/scan state is carried forward, never upgraded to `pass` from a failing mode.

**Boundaries:** It neither calls collectors nor parses `SUMMARY.md`, raw manifest, event/Defender data or captured console streams. It creates a brand-new JSON snapshot with exclusive create, no overwrite, outside the repository checkout. The output is limited to the gate's 32 KiB bounded schema and contains no host/build/path/identity/free-text fields. Generic errors and fixed success text do not echo supplied values. On POSIX it requests owner-only file mode; Windows permissions and profile synchronization still require *local human inspection*, and path replacement/reparse, parent ACL, cloud sync or a hostile same-user process are **not** solved by the helper. No upload, cleanup, privileged operation or production `src/` change.

**NO-GO:** The recorder exits 0 only to indicate a new *local metadata file* was created; **this is not readiness**. ADR-031 `field_evidence_gate.py` always reports `decision=NO_GO` and exits 2 even for all-pass invented metadata. The recorder never changes provider-negative or security-review flags, and neither utility authenticates observation, initial root, enterprise policy or release authority.

**Regression:** Synthetic Python tests cover five-label completeness, duplicates/unknown/free-text and inconsistent modes, fail/scan priority, pending preservation, template/source rejection, re-entry/output-collision refusal, no path or canary echo, out-of-repository creation, and a downstream NO-GO/exit-2 check. Run tests in both hosted Windows PowerShell 5.1/7 CI jobs as ordinary Python steps. Real Windows 10/11 devices, approved privilege contexts, initial root trust and privacy/ACL field review remain open in #2/#3.

## ADR-033 (2026-11-01): fail-closed strict JSON and descriptor-bound field metadata reads (PR #38)

**Issue:** Python's default JSON decoder silently accepts duplicate object keys using the last occurrence, and accepts nonstandard `NaN`/`Infinity`. A manually transcribed field-evidence file with contradictory keys could consequently appear valid after earlier fields disappear. ADR-031's checker also used a separate `is_file/stat/open` sequence, and ADR-032's recorder maintained an independent permissive parser. These are integrity and privacy-boundary ambiguities, **not** evidence that user reports have leaked.

**Decision:** Implement a shared, dependency-free `load_evidence` in `tools/field_evidence_gate.py`, reused by the PR #37 recorder. Reject duplicate keys *at every nesting level*, non-finite JSON constants, non-regular files, file-level symlinks/reparse objects, file-object mismatch between `lstat` and the opened descriptor, and inputs over 32 KiB. On POSIX, request `O_NOFOLLOW` and nonblocking read to limit symlink/FIFO substitution; on Windows, check the file's reparse attribute before the open, then compare descriptor metadata after opening. `read_evidence` and both CLIs fail closed with fixed labels or fixed errors; no user paths, argument values or raw metadata are printed for invalid input. No new telemetry or output artifacts.

**Limitations:** This read-side check is not an authenticated provenance proof, a stable file-ID attestation, an atomic traversal of **parent** directories, or protection against an adversary who controls a writable ancestor or the same account. The recorder's *output* ACL and redirected/synced location still need local review (ADR-032/#3); do not imply Windows private DACL enforcement. A path may change before `os.open`; the identity comparison is an early detection layer, not a complete TOCTOU solution. No production `src/` changes, native scans, report collection, changes to release status, or automatic publication.

**Regression:** Extend both Python synthetic suites with root/nested duplicate JSON fields, unusual JSON constants, links, non-regular file/FIFO rejection where supported, fixed CLI error messages without secret echo, and downstream recorder refusal to create an output from ambiguous metadata. These suites already run in both hosted Windows PowerShell 5.1 and PowerShell 7 jobs. Both remain hosted CI, **not physical Windows 10/11 validation**. ADR-031 continues to report `decision=NO_GO` / exit code 2, even for complete self-asserted statuses; issues #2 and #3 remain OPEN.

## ADR-034 (2026-11-01): observational field-status file ACL review and sync ambiguity (PR #39)

**Risk.** The optional ADR-032 Python status recorder uses `os.open(..., O_EXCL, 0o600)`; that mode does **not** imply a protected Windows DACL. Files normally inherit their security descriptor from the parent directory when a custom descriptor is not supplied at file creation. A status-only snapshot can reveal testing activity. Even a locally restricted ACL cannot establish that OneDrive/Known Folder Move, backup/sync agents, privileged users, or enterprise DLP did not replicate bytes. The recorder currently refuses in-checkout output but does not itself enforce a private Windows DACL; pretending otherwise would create false assurance.

**Decision.** Add a separately invoked **read-only, observation-only** `Test-WtFieldStatusAcl.ps1`, backed by `tools/WinTriage.FieldStatusAclReview.psm1`. It reads only filesystem metadata (leaf attributes, directory ancestry, owner SID and DACL) for an **explicitly supplied existing** local status file. It never reads JSON bytes or any raw report, modifies access rights, changes sync settings, uploads, or records a log. It produces fixed, non-identifying labels `MetadataAcl=restricted|review`, `PathObservation=direct_local_observed|review`, `SyncAndBackup=unknown` and `Decision=NO_GO`. Its CLI **always exits 2** even when ACL observations are restricted. Owner must be the current user, SYSTEM or Administrators; all access rules must be Allow for exactly those SIDs and each required SID must have FullControl. Unknown owners, other principals (including Everyone), explicit Deny, unreadable ACL and nonlocal/reparse paths force `review`.

**Security boundaries.** `restricted` indicates a *point-in-time structural check only*, not a certified effective-access proof; privileges, auditing, parent modification, domain policy, backup, EFS/BitLocker and reparse/path swaps remain separate. Lexical DriveInfo and reparse checks cannot establish a trusted initial root or eliminate TOCTOU; the path is opened by name again for ACL inspection. `direct_local_observed` does not mean unsynchronized: Windows Known Folder Move can sync ordinary paths without a uniform file flag. No `safe` sync classification is emitted. The new code remains outside production `src/` and does not cause normal scans or reports to run.

**Synthetic evidence.** In each hosted Windows 5.1/7 CI job, create a fresh GUID-owned temporary folder and a private subdirectory using the existing creation-time report DACL test boundary. Run the real Python status recorder against an invented template **only within that fixture**, classify the resulting file's inherited actual ACL without reading content, and verify fixed-label output and NO-GO exit. In-memory foreign-owner/Everyone ACL negative controls and test-owned junction-ancestor negative control run without modifying existing reports or user ACLs. Test removes only its GUID fixture. This is hosted CI **not physical Windows 10/11 field evidence** and does not license a migration of the recorder's write path to new native APIs. Keep issue #2/#3 OPEN and release NO-GO.

**Microsoft references.** https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights ; https://learn.microsoft.com/en-us/windows/desktop/FileIO/creating-and-opening-files ; https://learn.microsoft.com/sharepoint/redirect-known-folders .

## ADR-035 (2026-11-01): research-only create-time DACL on a new fixed-status file (PR #40)

**Motivation:** ADR-034 showed a status-only Python snapshot created with `os.open(O_EXCL, 0o600)` can receive its Windows ACL from its parent, and subsequent read-only permission observation is not a secure creation primitive. Adding `Set-Acl` after writing would expose a time interval of default permissions. A test-only Windows create-time experiment should establish the behavior of `CreateFileW` with an explicitly supplied descriptor, without implying production safety.

**Decision:** Add `tests/FieldStatusFileCreateProbe.cs` and `tests/FieldStatusFileCreateProbe.Tests.ps1`, **strictly research-only**, not in `src/` and never imported by the real recorder. The P/Invoke calls `CreateFileW` with `SECURITY_ATTRIBUTES.lpSecurityDescriptor` holding a preconstructed protected `FileSecurity` descriptor; uses `CREATE_NEW` (no replacement), no sharing, a non-inheritable handle, and bounded synthetic-only content through the returned handle. It does not create an unprotected file and later apply `Set-Acl`. The separate *test-owned* policy guard refuses unknown owners, Everyone, missing required SYSTEM/Administrators, inherited DACLs and non-allowlisted access before the call. This guard is essential: the native function **accepts descriptors supplied by callers**, not a guarantee of our allowlist.

**Evidence design:** Each hosted Windows PowerShell 5.1 and PowerShell 7 job creates only a fresh GUID-owned disposable private folder using the existing synthetic test API and writes an invented JSON payload. Inspect the actual file DACL after the exclusive native open/write; verify protected inheritance, intended SID allowlist/owner, no inherited ACEs, and ADR-034's read-only observer returning `MetadataAcl=restricted`, `SyncAndBackup=unknown`, `Decision=NO_GO`. Try creating the same file again and ensure both its bytes and ACL remain unchanged. In-memory weak-descriptor negative cases must leave no output. No use of host reports, network, repair tools, Defender/ClamAV, ACL mutation on existing files, or user data.

**Limits:** This P/Invoke accepts a *path string* rather than a held, independently authenticated parent directory handle; a malicious ancestor swap, junction, mount/remote alias, or same-user process can still redirect the target. The fixture inherits the previous test trust assumptions. The observed ACL is checked *after* the handle closes, not a production-grade handle-authenticated check during a write. `0o600` in the current production-independent Python helper remains **unchanged and not guaranteed secure**. Future release work requires independent trusted initial root, real Windows 10/11 fixed-drive and managed-profile ACL/sync validation, a reviewed production integration strategy, and authorized privacy/security release approval. No new `GO` outcome is allowed; issues #2/#3 remain OPEN.

**Microsoft API references:** https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights ; https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew .

## ADR-036 (2026-11-01): test-only held-parent relative status file creation and returned-handle ACL (PR #41)

**Problem.** ADR-035 demonstrated create-time file DACL with Win32 `CreateFileW` but accepted an absolute path string. Between parent inspection and file creation, the original directory name may be renamed and replaced by a decoy, possibly redirecting sensitive status data. A relative operation on a *held* parent handle can reduce that particular name-lookup race. It cannot authenticate the original root.

**Decision.** Research only, add `tests/RelativeFieldFileProbe.cs` plus PowerShell synthetic fixtures. The probe opens a test-owned parent with `CreateFileW` requesting `FILE_ADD_FILE`, `READ_CONTROL` and `FILE_FLAG_OPEN_REPARSE_POINT`, rejecting directory handles with the reparse attribute. It then uses `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory = parent.DangerousGetHandle()`, a strict single-leaf `.json` name, `FILE_CREATE` (never `FILE_OPEN_IF` or overwrite), `FILE_NON_DIRECTORY_FILE`, a preconstructed protected file security descriptor and a borrowed parent-handle reference. It checks that the returned handle is a regular non-reparse file. The caller reads owner/DACL with `GetKernelObjectSecurity` on **that same returned handle before writing** invented data to it. It never writes real diagnostic data and never reparses the parent path at file create time.

**Synthetic negative controls.** Both Windows PowerShell 5.1 and 7 hosted jobs test creation and read-back of invented bytes; protected DACL owner and allowlist, exclusive same-name collision preserving ACL and bytes, malformed names, empty security descriptor, disposed parent handle, and a synthetic parent directory rename followed by a decoy at the old path. If the host permits the rename, the second file must exist only below the *moved original held parent*; never in the decoy. If the runner denies rename, the test reports that optional fixture was not exercised rather than claiming proof. A test-owned parent junction must be refused when creation of a junction is permitted. No user report paths, privilege escalation, cleanup outside GUID scratch, or uploads.

**Security boundary / NO-GO.** `NtCreateFile` interop is a **research-only** native API experiment rather than a supported cross-version product contract. Parent pinning by an untrusted name is not an authenticated anchor; ancestor namespace substitution, mount and redirect points, filesystem policy, arbitrary alternate aliases, same-user malicious processes and real Windows 10/11 environments remain unverified. A file's ACL observed on its returned handle does not prove that the data has never been synced/backed up or that its initial root is trustworthy. This probe is **not imported into `src/`**, the real Python status recorder, or the field evidence gate. Release always `NO_GO`, both #2/#3 stay OPEN. Do not use this probe to gather customer or local diagnostic evidence.

**References:** Microsoft `NtCreateFile` OBJECT_ATTRIBUTES RootDirectory and FILE_CREATE documentation: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-ntcreatefile . Earlier research ADR-025 (relative directory creation), ADR-035 (create-time DACL).

## ADR-037 (2026-11-01): externally held synthetic reference versus self-certified decoy for file creation (PR #42)

**Problem.** ADR-036's `RelativeFieldFileProbe.PinSyntheticParent(path)` binds a filesystem operation to the resulting handle, but does **not** authenticate that the initial path was authoritative. An attacker able to substitute the parent before the first open can supply a valid, internally consistent *decoy* object. A verifier must not silently derive its own trust baseline from the same untrusted candidate.

**Research decision.** Add `tests/AnchorBoundFieldFileSession.cs` and a GUID-owned synthetic Windows fixture only. The session requires two **distinct borrowed handles**: an externally held synthetic reference acquired earlier, and a separately opened candidate parent. It delegates to ADR-030's `SyntheticAnchorLease` to compare full 128-bit `FileIdInfo` plus volume identity under an explicit nonempty session epoch, rechecking live reference/candidate handles before and after ADR-036's `NtCreateFile` `FILE_CREATE` operation. The returned file handle's ACL is checked before the caller writes invented JSON bytes. A retired session or a closed reference handle fails closed. The helper neither searches for anchors nor makes real evidence or release decisions. It uses an existing synthetic-only absolute parent opener; it never claims to authenticate that first reference's origin.

**Negative controls.** First create under an independently held synthetic reference and a different matching candidate handle; reject a duplicate leaf while retaining bytes/ACL. If the CI runner permits rename, move the original directory, replace its former name with a same-volume decoy, demonstrate that a freshly opened decoy candidate **fails against the earlier held reference**, and that the original pinned candidate's file creation remains beneath the moved original rather than the decoy. Then demonstrate the opposite counterexample: *a decoy reference plus a decoy candidate can pass object-identity checks*, proving the implementation **cannot establish provenance** without a truly external authenticated reference. No file is created for that forged example. Wrong epoch, same-handle-as-reference, revoked session and closed reference must fail.

**Boundaries.** This is *only* a test of an injected trusted-reference assumption—not proof that such a reference exists on a physical PC. An administrator, malicious same-user process, profile redirection, mount point, filesystem policy or compromised source can still supply a plausible handle; no trust authority is established and no real device evidence is collected. The native helper is under `tests/` only, never imported by `src/`, the optional Python status recorder or NO-GO gate. There is no automatic scan, upload, deletion or change to customer reports. Real Windows 10/11 field validation, managed/OneDrive/backup privacy checks, origin verification and independent approval remain open (#2/#3); release remains `NO_GO`.
